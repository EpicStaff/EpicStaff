# CORS allow-list (Django, realtime, webhook)

## Why this exists

Django (`django-cors-headers`) and Starlette's `CORSMiddleware` (used by the
realtime and webhook services) don't send a literal `*` when
`allow_credentials`/`CORS_ALLOW_CREDENTIALS` is enabled — they **reflect the
request's `Origin` header back**. Combined with a wildcard origin config,
that let any website a logged-in user visited make authenticated cross-origin
requests using that user's session and read the response. Security review
finding #44 flagged this on Django, the realtime service, and the webhook
service. All three have now been fixed.

## How it's configured

### Django and realtime

`CORS_ALLOWED_ORIGINS` is a single comma-separated env var, shared by both
services:

- Django reads it in `src/django_app/django_app/settings.py` and computes
  the fallback via the shared `resolve_cors_allowed_origins()` helper in
  `src/shared/cors.py`.
- realtime reads it in `src/realtime/core/config.py`
  (`Settings.cors_allowed_origins_list`, which calls the same shared helper)
  and consumes it in `src/realtime/api/main.py`'s `CORSMiddleware` setup.

**If unset, it falls back to `FRONTEND_BASE_URL` plus `http(s)://DOMAIN_NAME`.**
Every deployment already sets `FRONTEND_BASE_URL` to its real frontend domain
(it's load-bearing today for password-reset email links), and `DOMAIN_NAME` is
what the `epicstaff-nginx` service (`src/docker-compose.yaml`) actually serves
the whole stack on. These are two different local topologies — a raw
`ng serve` dev server (`FRONTEND_BASE_URL`, typically `http://localhost:4200`)
vs. the full docker-compose stack behind nginx (`DOMAIN_NAME`, typically
`localhost` on port 80/443) — so both are trusted by default and this fix
requires **no action** on already-deployed `.env` files.

### Webhook

The webhook service (`src/webhook/app/main.py`, `src/webhook/app/core/settings.py`)
follows the same pattern and the same `CORS_ALLOWED_ORIGINS` /
`FRONTEND_BASE_URL` / `DOMAIN_NAME` fallback, via the same shared
`resolve_cors_allowed_origins()` helper (`src/shared/cors.py`), through its
own `Settings.cors_allowed_origins_list` property. Unlike Django/realtime, it also sets
`allow_credentials=False` — the webhook service has no cookie-based auth at
all (no session, nothing to protect with credentialed CORS), so allowing
credentials would have protected nothing while widening the attack surface
for no benefit.

Only set `CORS_ALLOWED_ORIGINS` explicitly when a deployment needs to trust
more than one origin, e.g.:
```
CORS_ALLOWED_ORIGINS=https://app.example.com,https://admin.example.com
```

## Where the var is defined

Like every other env var in this repo, `CORS_ALLOWED_ORIGINS` is declared once
in `src/env.yaml` (the source of truth) and flows into `src/.dev.env`,
`src/debug.env`, and `src/.env.example` via `python scripts/generate_env.py`.
**Never hand-edit those three generated files** — edit `env.yaml` and
regenerate. The real, per-deployment `src/.env` is not generated by this
script; it's created once from `.env.example` and lives outside version
control on each server. `FRONTEND_BASE_URL`, `DOMAIN_NAME`, and
`CORS_ALLOWED_ORIGINS` are passed through explicitly in each of the
`django_app`, `realtime`, and `webhook` services' `environment:` blocks in
`src/docker-compose.yaml` (they are not in the shared `x-common-env` anchor,
since other services in the compose file don't need them).

## Do not reintroduce the wildcard

If a future change needs to widen CORS, do not go back to
`CORS_ALLOW_ALL_ORIGINS = True` / `allow_origins=["*"]` while credentials are
allowed — that's exactly the reflected-origin behavior this fix closes. Add
the new trusted origin to `CORS_ALLOWED_ORIGINS` instead.
