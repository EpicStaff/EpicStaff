# Signing keys

EpicStaff has two signing keys, both set as environment variables:

| Variable | Used for | Read by | Required |
| --- | --- | --- | --- |
| `DJANGO_SECRET_KEY` | Django's `SECRET_KEY` — sessions, JWT access and refresh tokens, and the encryption key for stored Secrets | `django_app` | Yes |
| `AUDIT_JWT_SECRET` | Short-lived audit tokens that `django_app` mints (`POST /api/audit/token/`) and `auditor` verifies locally | `django_app`, `auditor` | Yes |

There is **no separate JWT signing key**. Access and refresh tokens are signed with
`DJANGO_SECRET_KEY` — `src/django_app/django_app/settings/jwt.py` sets
`SIMPLE_JWT["SIGNING_KEY"]` to `SECRET_KEY` directly. A `JWT_SECRET` variable is not read
by anything; setting it has no effect.

`AUDIT_JWT_SECRET` is deliberately separate from `DJANGO_SECRET_KEY`, so the auditor can
verify audit tokens without ever holding Django's key.

## How a missing or blank key fails

- `DJANGO_SECRET_KEY` is read with `env.secret` (`src/shared/envtools.py`), which strips
  surrounding whitespace and raises `EnvironmentNotFoundError` when the variable is absent
  and `EnvironmentBlankError` when it is empty or whitespace-only. `src/docker-compose.yaml`
  enforces it one layer earlier with `${DJANGO_SECRET_KEY:?}`, so an unset or empty value
  fails before a container is created.
- `AUDIT_JWT_SECRET` is required by `src/docker-compose.yaml` for both `django_app` and
  `auditor` (`${AUDIT_JWT_SECRET:?}`). Both services read it with `env.str`, which rejects a
  missing variable but accepts an empty one — outside compose, never set it to a blank
  value.

## Generating a key

```bash
openssl rand -base64 48 | tr -d '=+/'
```

PowerShell (Windows):

```powershell
$bytes = [byte[]]::new(48); [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes); [Convert]::ToBase64String($bytes) -replace '[=+/]'
```

Don't use `Get-Random` for keys — it is not a cryptographic generator.

Any random string of 50+ characters works. Avoid `$` (Docker Compose treats it as
interpolation) and `#` (env files treat it as a comment). Generate a different value for
each of the two keys.

`python scripts/envtool.py --dev` fills both keys with fixed development values
(`src/env.yaml`). Those are public — never use a `--dev` env file for a deployment.

## Generate once, then keep it

**Do not rotate `DJANGO_SECRET_KEY` casually.** Changing it:

- invalidates every existing session and every issued access and refresh token;
- makes every stored Secret permanently unreadable — Secret values are encrypted with a
  key derived from `DJANGO_SECRET_KEY` (`src/django_app/tables/services/secrets/encryption.py`).

API keys are not affected: they are stored as plain SHA-256 hashes, independent of
`DJANGO_SECRET_KEY`.

Changing `AUDIT_JWT_SECRET` only invalidates outstanding audit tokens, which are
short-lived (`AUDIT_TOKEN_TTL_SECONDS`). `django_app` and `auditor` must always hold the
same value.

Generate each value once when you first set up a deployment, store it with your other
deployment secrets, and reuse it. If you regenerate `src/.env` from
`src/.env.example`, carry the existing keys across rather than making new ones.

## Where each deployment path gets its keys

| Path | Source |
| --- | --- |
| `docker compose up` in `src/` | `src/.env`, generated by `python scripts/envtool.py` or copied from `src/.env.example` — see the Quick Start in the README |

`src/.env` is gitignored. Keep it out of version control and out of image builds.

Note that `src/.env` is read for *interpolation*, and `src/docker-compose.yaml`
declares no `env_file:` entries, so each key reaches only the services that name it:
`DJANGO_SECRET_KEY` reaches `django_app` only, `AUDIT_JWT_SECRET` reaches `django_app`
and `auditor`.
